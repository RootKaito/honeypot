chapter 06

Lessons Learned

What's left after building this from scratch, and where to go from here.

Principles that held up in practice

  • Two independent sources of truth beat one sophisticated one. The honeypot and the IDS never depended on each other to work — when one had a configuration problem, the other kept logging normally, and that independence was what made diagnosis possible at several points.
  • A minimal container cuts both ways. Cowrie's image not having basic utilities is great for reducing attack surface, but it also breaks common debugging habits (like using docker exec ... tail) — always worth checking what an "official" image actually contains before assuming.
  • IPv4 and IPv6 are two different exposure surfaces. A firewall rule written with only IPv4 in mind can leave a whole hole on the IPv6 side, with no obvious sign that it happened.
  • "No error" isn't the same as "working." More than once, a service came up without complaining (Suricata with the wrong interface, Alloy without read permission) and simply didn't do what it was supposed to, silently. Validating the end-to-end result matters more than trusting "no error appeared."
  • Snapshots change your relationship with risk. Having the option to return to a clean state in seconds makes it safer to test riskier changes than would be reasonable to attempt on physical hardware without that safety net.
the end result

A honeypot receiving real, unsolicited attempts from the internet, an IDS independently classifying that traffic, and a dashboard showing both sides of the story in real time — built, broken, and fixed enough to become this guide.

Possible next steps

  • Geolocation enrichment. A GeoIP lookup stage (MaxMind GeoLite2) before logs reach Loki enables a map panel showing where attempts come from.
  • More honeypot protocols. Cowrie covers SSH/Telnet; there are honeypots specialized in other services (HTTP, databases, RDP) that could run in parallel, each on its own isolated network.
  • Active alerting. Instead of only watching the dashboard, configure Grafana to notify (email, webhook) when a specific pattern shows up — a spike in attempts, or a high-severity Suricata signature.
  • Move to dedicated hardware. If the lab is running in a VM on your everyday machine, it's worth considering moving it to its own device once the setup is validated — it shrinks the worst case of an isolation failure back down to "just that device," not your work machine.
