chapter 04

Exposure & Dashboard

Opening the honeypot to the real internet, and building the panel that shows what comes in.

Check for CGNAT before anything else

Residential providers (fiber, especially) sometimes don't hand out a real public IP — the customer sits behind a NAT shared by the carrier itself (CGNAT). If that's the case, no port-forward will ever work, no matter how correct the configuration is.

curl -4 ifconfig.me

Then, from a browser on the same network, open canyouseeme.org, type the port you plan to expose, and click Check. This confirms whether the forward is reachable from outside before you spend time debugging something that might be structurally impossible on your end.

note

If you confirm CGNAT, traditional port-forwarding won't work — the alternatives are asking your provider for a public IP, or using a reverse tunnel (Cloudflare Tunnel, for example), which changes this guide's architecture.

Configure port forwarding

In your router's admin panel (the menu name varies by vendor: Port Forwarding, Virtual Server, NAT), create two rules:

FieldSSH ruleTelnet rule
External port2223
Internal port22222223
Internal IPVM_IP
ProtocolTCP

Test from truly outside (mobile data, not Wi-Fi on the same network):

ssh -p 22 root@YOUR_PUBLIC_IP

It should drop you into Cowrie's fake shell.

Centralizing logs: Grafana Alloy

The agent that reads log files and ships them to the log database (Loki) runs natively on the VM — not in a container, for the same reason as Suricata: it needs direct access to the filesystem.

about the choice

The agent traditionally used with Loki (Promtail) has been discontinued — the official replacement is Grafana Alloy, which uses its own configuration language (River) instead of YAML.

sudo mkdir -p /etc/apt/keyrings
sudo wget -qO /etc/apt/keyrings/grafana.asc https://apt.grafana.com/gpg-full.key
sudo chmod 644 /etc/apt/keyrings/grafana.asc
echo "deb [signed-by=/etc/apt/keyrings/grafana.asc] https://apt.grafana.com stable main" | sudo tee /etc/apt/sources.list.d/grafana.list

sudo apt update
sudo apt install -y alloy
local.file_match "suricata" {
  path_targets = [{"__path__" = "/var/log/suricata/eve.json", "job" = "suricata"}]
}

local.file_match "cowrie" {
  path_targets = [{"__path__" = "/var/lib/docker/volumes/cowrie-honeypot_cowrie-var/_data/log/cowrie/cowrie.json", "job" = "cowrie"}]
}

loki.source.file "suricata_tail" {
  targets    = local.file_match.suricata.targets
  forward_to = [loki.write.local.receiver]
}

loki.source.file "cowrie_tail" {
  targets    = local.file_match.cowrie.targets
  forward_to = [loki.write.local.receiver]
}

loki.write "local" {
  endpoint {
    url = "http://127.0.0.1:3100/loki/api/v1/push"
  }
}
the permission that almost always gets missed

Alloy runs as its own system user (alloy), not root. The /var/lib/docker folder usually ships with drwx--x--- permissions — only root and the root group can traverse it. That blocks Alloy from reaching Cowrie's log, even though the log file itself has read permission open. Fix it with a targeted ACL, without opening the folder to anyone else:

sudo setfacl -m u:alloy:x /var/lib/docker
getfacl /var/lib/docker | grep alloy   # confirms: user:alloy:--x

sudo systemctl enable --now alloy
sudo journalctl -u alloy --since "30 seconds ago" --no-pager | grep -i tailing

Two lines saying "start tailing file" should show up — one for Suricata, one for Cowrie.

Loki + Grafana

Both run in separate containers, so they need a shared Docker network to see each other — 127.0.0.1 from inside one container points at itself, not at its neighbor.

docker network create dashboard-net

mkdir -p ~/honeypot-dashboard && cd ~/honeypot-dashboard
wget https://raw.githubusercontent.com/grafana/loki/v3.7.0/cmd/loki/loki-local-config.yaml -O loki-config.yaml

docker run --name loki -d \
  --network dashboard-net \
  -v $(pwd):/mnt/config \
  -p 127.0.0.1:3100:3100 \
  grafana/loki:3.7.0 -config.file=/mnt/config/loki-config.yaml

docker run --name grafana -d \
  --network dashboard-net \
  -p 127.0.0.1:3000:3000 \
  grafana/grafana:latest

# make sure they survive a VM reboot
docker update --restart unless-stopped loki grafana
container name, not ip

Within the same Docker network, containers resolve each other by name via internal DNS — use http://loki:3100 as the Data Source URL in Grafana, not 127.0.0.1.

Access Grafana (which is bound only to 127.0.0.1) via an SSH tunnel:

ssh -p 2200 -L 3000:127.0.0.1:3000 user@VM_IP

With the tunnel open, access http://localhost:3000 in your machine's browser.

Building the panels

  1. Connections → Data sources → Add data source → Loki, URL http://loki:3100, Save & test.
  2. Dashboards → New → New Dashboard → Add visualization, pick Loki as the source.
  3. In the query editor, click Code (the default mode is visual and doesn't accept pasting the query directly) and paste one of the queries below.

Honeypot attempts over time

Visualization type: Time series.

sum(count_over_time({job="cowrie"}[5m]))

Suricata alerts by severity

Visualization type: Bar chart.

sum by (severity) (count_over_time({job="suricata"} | json | alert_severity != "" [5m]))

Top source IPs

Visualization type: Table.

topk(10, sum by (src_ip) (count_over_time({job="cowrie"} | json [1h])))
note

The severity panel will probably stay empty at first — Suricata's default ruleset tends to trigger more on pattern/count (several brute-force attempts in a window, for instance) than on a single isolated connection. It starts filling in as real attack traffic arrives.
