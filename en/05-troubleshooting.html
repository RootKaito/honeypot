chapter 05

Troubleshooting

Every error below really happened in a real implementation of this guide — none of these are hypothetical. Click any symptom to see the cause and the fix.

Network & packet capture

Suricata generates no alert at all, even with the ICMP test

cause

The interface name configured under af-packet doesn't actually exist on the machine — usually because it was copied from another context (eth0, common in generic guides or physical hardware, while VMs tend to use enp0s3 or similar). Suricata doesn't error out when started with a wrong interface, it just never captures anything.

fix

Run ip a on the machine itself, confirm the real name, and update the interface field under af-packet in suricata.yaml. Also check that HOME_NET points to the machine's real IP, not a sample address.

Cowrie logs show source IP 172.18.0.1 instead of the expected IP

cause

That's the Docker network's internal gateway — it shows up when the test is done from inside the VM's own host (ssh -p 2222 root@localhost), not from another point on the network.

fix

Not a configuration error. To validate "real" traffic capture, always test from another machine on the network, never from inside the VM itself.

SSH access

Connection refused when trying to SSH on a port that worked before

cause

The sshd service may have gone back to listening on the default port (22) instead of the configured management port — an upgrade of the openssh-server package can restore the original sshd_config if the package manager treats the file as unmodified, depending on how a conflict prompt was answered.

fix

Confirm with sudo ss -tlnp | grep ssh which port it's actually listening on. If the hardening lines in sshd_config are commented out (with # in front), uncomment them and restart the service. Prevention: sudo apt-mark hold openssh-server once everything has stabilized.

Permission denied (publickey) even with the key configured

most common cause

Running the SSH command with sudo in front changes which user (and therefore which private key) is used — sudo ssh ... looks for the key in /root/.ssh/, not your normal user's folder.

second possible cause

The public key was never actually copied into the right user's authorized_keys — especially easy to happen if clipboard sharing between host and VM is disabled (recommended for security) and the key was pasted manually, with a character lost along the way.

fix

Never put sudo in front of a plain ssh command. To copy the key without relying on manual pasting, use ssh-copy-id -p PORT user@IP — avoids the problem entirely.

Docker & containers

network ... declared as external, but could not be found

cause

docker-compose.yaml references a network marked external: true — meaning it expects the network to already exist — but it was never created.

fix

docker network create network-name before docker compose up.

exec: "tail": executable file not found in $PATH inside the Cowrie container

cause

The official Cowrie image is minimal on purpose (fewer binaries = smaller attack surface if someone escapes the sandbox) — it doesn't include tail or other coreutils utilities.

fix

Use docker logs cowrie --tail 20 (reads via Docker's own log driver, doesn't depend on anything inside the container) or read the file directly from the volume, on the host.

Grafana: Unable to connect with Loki

cause

Grafana and Loki running in separate Docker containers don't share 127.0.0.1 — each container has its own isolated loopback. Using http://127.0.0.1:3100 as the Data Source URL points Grafana at itself, not at Loki.

fix

Put both containers on the same dedicated Docker network and use the container name as the hostname (http://loki:3100) — resolved via Docker's internal DNS, available only between containers on the same network.

Query in Grafana Explore ({job="cowrie"}) always returns no results

cause

Alloy runs as a non-root system user. The /var/lib/docker folder usually has drwx--x--- permissions, which blocks users outside the root group from even traversing that folder — even though the final log file has read access open, the chain breaks somewhere in the middle.

how to diagnose

sudo namei -l /full/path/to/file.json lists the permissions of every folder in the path, one per line — shows exactly where the chain breaks.

fix

sudo setfacl -m u:alloy:x /var/lib/docker — grants traverse permission only to Alloy's user, without opening the folder to anyone else.

Internet exposure

External SSH just hangs, no response at all (no refusal, no clear timeout)

possible causes

The port-forwarding rule isn't configured on the router yet, or the internet provider uses CGNAT (carrier-shared NAT) — in that second case, the packet never even reaches your router.

fix

Confirm the real public IP with curl -4 ifconfig.me and test with canyouseeme.org before insisting on tweaking the router's configuration. If CGNAT is confirmed, traditional port-forwarding isn't an option — consider asking the provider for a public IP or using a reverse tunnel.

Firewall opening the management port to "Anywhere" instead of the local network

cause

A rule created without restricting the source (ufw allow PORT/tcp, without from) opens the port to any IPv4 and any IPv6 — IPv6 doesn't go through the router's NAT the way IPv4 does, so this can expose the port to the internet even with no port-forward configured at all.

fix

sudo ufw delete allow PORT/tcp
sudo ufw allow from YOUR_SUBNET/24 to any port PORT proto tcp

Confirm in ufw status verbose that it shows your subnet, not Anywhere, and that there's no leftover (v6) line.

Discontinued tools

Downloading Promtail returns 404 Not Found

cause

Promtail was officially discontinued and removed from Loki's release repository — it's not a matter of the wrong version, the binary simply no longer exists.

fix

Use Grafana Alloy instead — same role (log collection agent), different configuration (River language instead of YAML). Details in chapter 4.

Normal behavior (not a bug)

Loki responds "Ingester not ready" for several minutes after starting up

what's happening

This is expected — Loki's internal "ring" stabilization process can take anywhere from 15 seconds to 1-2 minutes, depending on the machine. It's not a hang or a configuration error.

when to worry

If it goes past 2-3 minutes without ever becoming ready, then it's worth investigating — check the system clock (VMs sometimes drift) and the container logs with docker logs loki.
