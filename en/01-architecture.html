chapter 01

Architecture & Threat Model

Before installing anything, it's worth understanding why the pieces are separated the way they are — and what can go wrong in the lab itself, not just in the honeypot.

The four pieces

The honeypot (Cowrie) and the network sensor (Suricata) watch the same traffic in two different, independent ways. Cowrie pretends to be a vulnerable SSH/Telnet server and logs everything a visitor tries to do inside it. Suricata knows nothing about that theater — it just watches network packets arriving on the interface, and recognizes patterns (an SSH attempt, a port scan, a known exploit signature) regardless of what's behind them.

That independence is the whole point: if Cowrie fails silently, or if someone finds a way to escape its sandbox, Suricata keeps seeing the traffic anyway — it operates at a layer below, straight on the network interface.

why this works even with the container in the middle

Suricata captures in af-packet mode, which operates below the layer where Docker rewrites addresses via NAT/iptables. That means it sees the real external port (the one exposed to the internet), not the container's internal port — correlation between the two systems stays consistent even with Docker in the middle.

Suricata runs native, outside any container, because it needs direct, low-level access to the network interface — adding a layer of Docker network virtualization in the middle only adds complexity with no benefit. Cowrie, on the other hand, is exactly the component that benefits most from isolation, since it's the one deliberately exposed to the world — so it lives inside a container, on a dedicated Docker network, with no route to anything else on the machine.

Network isolation

The general rule: only the honeypot's ports are reachable from outside. Everything else — SSH management of the machine, the Grafana dashboard, the Loki API — stays restricted to the local network or to 127.0.0.1, never exposed.

  • SSH management port: only accepts connections from the local network.
  • Grafana and Loki: bound to 127.0.0.1, accessed via SSH tunnel when needed — never published on the network.
  • Only two ports are actually forwarded on the router: Cowrie's (fake SSH and Telnet).
warning · ipv6

If your network has public IPv6, firewall rules created carelessly can open a port to the entire internet without any port-forward ever being configured — IPv6 doesn't go through NAT the way IPv4 does. Always check both stacks (v4 and v6) when reviewing firewall rules. More on this in the troubleshooting chapter.

The lab's own threat model

Framework applied: STRIDE, focused on the surface this project introduces on the network — the honeypot receiving attacks is expected; the real risk is what happens if the isolation fails.

ThreatScenarioMitigationPriority
Elevation of privilege Cowrie sandbox escape failure, execution on the host behind the container Container without --privileged, non-root user, isolated Docker network, always up-to-date image high
Tampering with evidence Attempt to delete local logs to cover tracks, after a compromise Logs replicated near real-time off the host (Loki), not dependent only on the local copy high
Information disclosure Dashboard or Loki API accidentally publicly reachable Bind exclusively on 127.0.0.1, never forwarded on the router high
Denial of service Connection volume saturates the machine's CPU/RAM, taking down the IDS itself Resource limits on the container, Suricata ruleset sized to the available hardware medium
Spoofing Confusion between the real management service and the honeypot, if on the same port/network SSH management on a non-standard port, only reachable from the local network medium
note

A honeypot receiving unsolicited traffic from the internet is an established practice — that's exactly what it's for. What needs to stay true is that it remains passive: it logs and simulates, never attacks back whoever tries to break in.

Running in a VM, on your main machine?

If the lab is going to run in a virtual machine inside the computer you use day to day (instead of dedicated hardware), it's worth adjusting expectations: the worst case of an isolation failure stops being "reflash a cheap device" and becomes "something escaped onto the machine you use for work." That doesn't rule the project out, but it justifies hardening the VM itself — disable clipboard and shared folders between host and VM, keep the hypervisor updated, and use snapshots.

a real advantage of the vm

Snapshots let you return to a clean state in seconds — take one right after the OS is installed and hardened, before bringing up any service. It's a safety net that physical hardware doesn't offer without a full reflash.
