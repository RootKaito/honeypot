chapter 03

IDS + Honeypot

Suricata watching the network, Cowrie pretending to be an easy target — and confirmation that one correctly sees the other.

Suricata

sudo apt install -y suricata
suricata --build-info | head -20

Before configuring, find the real network interface name inside the VM — it's almost never eth0 in virtualized environments:

ip a
common mistake

In VirtualBox VMs the name is usually enp0s3; on other hypervisors it can be different still. Configuring Suricata with an interface name that doesn't actually exist on the machine doesn't produce any error on startup — it simply never captures a single packet, and the symptom becomes "no alert ever shows up," with no clear clue why.

af-packet:
  - interface: YOUR_INTERFACE

vars:
  address-groups:
    HOME_NET: "[VM_IP/32]"
sudo suricata-update
sudo suricata -T -c /etc/suricata/suricata.yaml -v
sudo systemctl enable --now suricata
sudo systemctl status suricata

Test rule

Before relying on real attack traffic (which only triggers count/pattern-based rules), confirm the alert pipeline works with something simple:

alert icmp any any -> $HOME_NET any (msg:"Local test: ICMP received"; sid:1000001; rev:1;)

Confirm local.rules is listed under rule-files in suricata.yaml, restart, and test from another machine on the network:

ping -c 3 VM_IP
sudo tail -n 5 /var/log/suricata/eve.json | jq 'select(.event_type=="alert")'

Cowrie

Create the isolated Docker network before bringing up the container — forgetting this step is the most common cause of errors at compose up time:

docker network create honeypot-net
services:
  cowrie:
    image: cowrie/cowrie:latest
    container_name: cowrie
    restart: unless-stopped
    networks:
      - honeypot-net
    ports:
      - "2222:2222"
      - "2223:2223"
    volumes:
      - cowrie-etc:/cowrie/cowrie-git/etc
      - cowrie-var:/cowrie/cowrie-git/var
    deploy:
      resources:
        limits:
          memory: 256M
          cpus: "1.0"
    environment:
      - COWRIE_HONEYPOT_HOSTNAME=web-prod-02
      - COWRIE_TELNET_ENABLED=yes

networks:
  honeypot-net:
    external: true

volumes:
  cowrie-etc:
  cowrie-var:
docker compose up -d
docker compose ps
disguise

Avoid hostnames close to the tool's default pattern (svr04) — something like srv-04 is still recognizable to anyone who's seen a Cowrie before. Go for something genuinely generic, like in the example above.

Inspect before exposing

ssh -p 2222 root@localhost
# any username/password is accepted — the honeypot's trap
# run a few commands, then `exit`
note

The official Cowrie image is minimal on purpose — it has no tail or other utilities inside the container. To see the log, use docker logs cowrie --tail 20 instead of docker exec.

Confirm Suricata sees Cowrie

From another machine on the network:

ssh -p 2222 fake_user@VM_IP
sudo tail -n 20 /var/log/suricata/eve.json | jq 'select(.dest_port==2222)'
confirmed signal

dest_port: 2222 matches Cowrie's external port — proof that Suricata sees the packet before Docker's NAT rewrite. And src_ip being the real IP of another machine (not something like 172.18.0.1, which is Docker's internal gateway) confirms the traffic actually went over the real network, not just the container's internal bridge.
